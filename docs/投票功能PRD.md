## 1. 背景与目标

### 1.1 现状与痛点

群里要聚一次，现在的流程是：几个人在群里聊出几家备选 → 有人把店名复制到微信 → 在微信里发起群投票 → 大家点选 → 结果和理由散落在聊天记录里。

这条链路里有**三次人工搬运**：候选搬进微信、投票搬进微信、结果与理由再搬回聊天记录。搬运本身不产生任何信息，纯粹是损耗；而且地点信息（地址、人均、评分）在搬运中全部丢失。

### 1.2 目标

把「这次去哪家」收回到群地图里：成员在地点库上直接投票，每人选一家并可写一句推荐理由，结果自动汇总，任何人打开就能看清**谁选了哪家、为什么**。

### 1.3 成败判据（唯一一条）

**做完之后，群里不再需要用微信的投票功能。**

因此「带投票参数的分享链接」与「一键复制结果文本」是**必须项**，不是锦上添花。如果最终仍要有人把结果手抄回群里，视为目标未达成。

### 1.4 非目标（本期明确不做）

- 不做定时截止与到点自动锁定
- 不做匿名投票、权重票、多轮淘汰、排序投票
- 不做与微信投票功能的互通
- 不做服务端推送通知（见 2.4 对「实时」的定义）
- 不做设备指纹、签到、投票白名单等防刷加固（见 2.2）

## 2. 已确认的产品决策

| 事项 | 决策 |
| --- | --- |
| 投票形式 | **单选**：一名成员在一个投票里只能投一家 |
| 候选来源 | **只从已有地点库中挑选**，不允许现场手输新店名 |
| 候选数量 | 2～8 家 |
| 投票标题 | 必填，≤30 字 |
| 推荐理由 | 选填，≤140 字，**只针对自己投的那一家**填写 |
| 结束方式 | **只有手动结束**，不做定时截止 |
| 结束权限 | **任何成员都可以结束**（理由见 2.1） |
| 发起权限 | 任何成员都可以发起 |
| 并发投票 | **同一时间只允许一个进行中投票**；要发起新的必须先结束上一个 |
| 结果可见性 | 实时可见：谁投了哪家、写了什么理由，全部公开 |
| 投票历史 | 已结束的投票可随时查看，只读回看；每页 20 条，可继续加载全部历史 |
| 入口 | 顶部浏览方式增加第三个标签「投票」（列表 / 地图 / 投票） |
| 分享 | 带投票参数的链接 `?poll=<id>`，点开直接落到该投票 |
| 结果输出 | 一键「复制结果」，生成可直接粘贴回微信群的文本 |
| 撤票 | 允许撤回自己的投票（回到未投状态） |

### 2.1 为什么「结束」也对所有人开放

这条与「只允许一个进行中投票」是绑定的：如果只有发起人能结束，发起人一旦不在场，**所有人都发不了新投票**，功能会卡死。

所以结束权限放宽到所有成员，用三道约束兜住误操作：

1. 结束前**二次确认**，文案明确写出「结束后所有人都不能再投」；
2. 记录**是谁结束的、什么时候结束的**，历史里可见；
3. 结束**不是删除**，结果完整留在历史中，随时可回看。

### 2.2 「一人一票」的真实强度（必须如实告知，不给错误预期）

成员身份是浏览器本地存储里的匿名令牌。清缓存、换手机、换浏览器都会变成新成员，因此同一个人**理论上可以投第二次**。

**这是信任约束，不是防刷机制。** 本期不做任何加固。缓解方式是把投票人与理由全部公示，异常一眼可见。

同理，分享链接是公开的：拿到链接的人填个昵称就能投票。这与整个产品「公开链接、只填昵称」的定位一致，属已知取舍（见主 PRD 第 4 节与[问题汇总](./问题汇总.md) Q5）。

### 2.3 候选为什么不允许现场手输

手输的店没有地址、没有坐标、没有封面、没有人均和评分，点开就是一张空卡片——而这恰恰又回到了「手动把信息搬进群里」的老路，与 1.3 的成败判据直接冲突。

需要新候选时的正确路径是：**先在应用里添加地点**（现有功能已支持粘贴识别与截图识别 + 自动定位），再发起投票。

### 2.4 「实时可见」的确切含义

**不是服务端推送。** 实现为：打开投票时拉取一次；投票进行中且页面处于前台时，每 10 秒轮询一次；页面隐藏或投票已结束时停止。

群人数在十人量级，这个精度足够，且不引入长连接的成本与复杂度。如果未来要求「别人一投我这边立刻跳动」，那是另一个需求。

## 3. 功能验收标准

### 3.1 发起投票

- 无进行中投票时，任意成员可发起：填标题 → 从地点库勾选 2～8 家 → 发布。
- 标题可提供预置短语快捷键；候选少于 2 家或多于 8 家时**明确报错**，不许静默截断或降级。
- 已有进行中投票时：「发起投票」入口置灰并提示「请先结束当前投票」；**服务端同样拒绝（409）**，不能只靠前端拦截。

### 3.2 投票

- 进行中的投票里，成员可选中任意一家候选，并可附一句 ≤140 字的理由。
- **改票**：再次选择另一家即为改票，旧票作废，同一成员永远只占一票。
- **撤票**：可撤回，撤回后回到未投状态。
- 投票结束后不能再投、改、撤（服务端返回 409）。
- 未设置昵称的成员必须先设昵称才能投票（沿用现有身份流程）。

### 3.3 结果展示

- 每个候选显示：店名、地址、**人均**、评分、票数、投票人（昵称 + 成员色头像）与其理由；本期投票页不展示封面。
- 候选地点被永久删除后，保留发起时的店名、地址、人均与评分快照，并标注「已从地图删除」；该候选仍可投，原有票数照算。
- **候选顺序固定为发起时的顺序，不按票数实时重排**——避免正在点的按钮因为别人投了一票就跳走。
- 票数用横向条形表达相对多少，条形长度与数字一致。
- 显示已投人数与可投总人数，并列出**还没投的成员昵称**，便于催票。
- 结束态：最高票标注「就这家」；**若最高票并列，必须明确提示「平票，需要再商量」，不允许静默挑一家**。

### 3.4 历史

- 「历史投票」列出所有已结束的投票，按结束时间倒序，显示标题、结束时间、结束人、票数最高的候选。
- 点开为**只读**详情：候选、票数、每人选择与理由、结束信息完整可查。
- 历史不提供删除入口（误建的投票可以结束掉；删除属后续可选能力）。

### 3.5 分享与结果输出

- 投票详情可生成链接 `https://qunliao-food-map.app.workbuddy.host/?poll=<id>`，在微信里点开直接落到该投票。
- 「复制结果」生成一段纯文本，包含：标题、已投/可投人数、候选按票数排列、每家的投票人与理由、未投名单。
- 复制出的文本必须与页面数据一致；平票时文本里必须写明「平票」。

### 3.6 不能破坏的既有功能（回归红线）

- **删除地点**：地点被投票引用后再删除，现有「作者／群主永久删除地点」功能不能被阻塞（详见[方案文档风险一](./投票功能方案.md)）。
- 列表、地图、添加地点、粘贴识别、截图识别、自动定位、点赞、评分、评论、照片、群主领取等既有功能不受影响。

## 4. 非功能与数据

- 适配 360～430px 手机视口与微信内置浏览器；触控目标不小于 44px。
- 新增数据存 D1，以**追加迁移文件**的方式维护，不改写已上线的旧迁移。
- 投票不影响 R2 与照片逻辑。
- **不新增任何密钥、不新增外部服务依赖**（这是刻意的：投票不应把可用性绑在第三方上）。
- 成员令牌沿用 `X-Food-Map-Token` 头传输（平台反向代理会覆盖 `Authorization`）。

## 5. 实现前补充确认（2026-10-01）

- 标题快捷短语：今天吃什么／周末去哪吃／团建地点。
- 历史每页 20 条，通过「加载更多」访问全部；不设只保留最近 20 条的总上限。
- 「以上一轮候选重新发起」不在本期。
- 「可投总人数」按已注册成员计算；结束后的统计以结束时已注册成员为界，不因后来加入的新成员增加。
- 投票页不展示候选封面，重点展示人均；地点删除后候选仍可投，并展示上述信息快照。
