## 2026-09-30 · 迁移到 WorkBuddy 站点托管并发布

### 为什么换托管

- `workers.dev` 这条路**已被证据排除，不需要再注册 Cloudflare 账号去验证**：本机绕过代理直连 `https://example.workers.dev/` 超时 12s 且拿不到 IP；`example.workers.dev` 经阿里 DNS 解析得 `108.160.169.179`（Dropbox 网段）、本机默认解析得 `104.244.43.231`（Twitter 网段），均为伪造地址；GreatFire 记录其自 2022-05-10 起持续被屏蔽，2026-09-21 仍为已屏蔽。
- `chatgpt.site` 的拦截是 Cloudflare 边缘策略，不是本地网络问题：该域名 DNS 正常解析到真实 Cloudflare IP，绕过代理直连返回 403，说明连接成功但被应用之前拒绝。改前端或重部署同一域名都不会有用。
- 选定 WorkBuddy 站点托管：`*.workbuddy.host` 解析到腾讯云北京 CLB `49.233.240.214`，属国内 IP，无需备案、无需自有域名、无额外账号。

### 架构：数据层未改写

- `wrangler dev --local` 下 D1 就是本地 SQLite 文件、R2 就是本地目录，因此 16 条 `/api/*` 路由、服务端权限模型、`drizzle` 迁移与原生 SQL **全部原样保留**，没有引入登录系统。
- 这也回避了一个产品冲突：WorkBuddy 云服务数据库是托管 PostgreSQL，且约束「未登录只能读显式公开表，私有数据必须先登录」——采用它会强迫群成员注册登录，与「打开即用、只填昵称」冲突。

### 新增 `scripts/sandbox-serve.mjs`

1. 状态目录默认 `$HOME/.qunliao-food-map/state`，**位于项目目录之外**：部署会把项目目录打包上传，状态放在项目内会在每次重新部署时被覆盖。

4. `.gitignore` 增加 `.dev.vars` / `.dev.vars.*`；群主口令只以 SHA-256 哈希形式存在于该文件，不进仓库。

## 2026-10-01 · 配色与首屏优化、底图切换到高德

### 需求来源

- 用户反馈成员代表色**太暗**（原方案大量使用深色，白字可读但整体发闷），要求提亮；同时要求做一轮移动端 UI 优化。
- 用户提供高德 Web JS API Key，要求把底图从 OpenStreetMap 换成高德（OSM 瓦片在国内实测不可用，底图一直是空白，见问题汇总 Q3）。

### 配色：为什么不能只"提亮"

- 「提亮」与「白字可读」对同一块背景色是**互斥**的：白字要满足 WCAG 4.5:1，背景相对亮度必须压在 L ≲ 52%；再提亮就只能改用深色字。
- 因此方案是**双管齐下**：把 8 个代表色统一收敛到 L 48.0～52.9%（对比度 ≥4.62:1），并让字色**按背景亮度自动切换**（`contrastText()` 返回 `#18302d` 或 `#ffffff`）。这样颜色确实亮了，字也始终可读。

### 实现

- 新增 `lib/color.ts` 作为**唯一色彩源**：`MEMBER_COLORS`（砖红／青碧／靛蓝／紫罗兰／琥珀／玫红／草绿／天蓝）、`MEMBER_COLOR_NAMES`、`contrastText()`、`memberColorStyle()`、`normalizeColor()`。
- 旧色迁移用**代码级映射**（`LEGACY_COLOR_MAP` + `normalizeColor()`）而不是 SQL：写入接口 `/api/members`、`/api/me` 与微信回调都会把旧值归一成新色，**旧数据不需要批量改库**，且映射可回退。未知或非法值回落到默认色。
- 把 `.member-avatar`、`.profile-illustration span`、`.color-option` 里写死的 `color:#fff` 全部移除，改为 `style={memberColorStyle(color)}`；`components/food-map-app.tsx`、`place-detail.tsx`、`profile-dialog.tsx`、`map-canvas.tsx`、`amap-canvas.tsx` 同步接入。
- UI 优化：色块触控目标 38→44px（对齐 iOS 最小触控尺寸）、配色块补 `aria-label`（中文色名）、清理 20 个已无引用的死 CSS 类（`.brand`、`.list-add-button`、`.places-panel` 等）。

- `app/api/map/config/route.ts` 不再强制要求 `AMAP_SECURITY_JS_CODE`：有 `AMAP_WEB_KEY` 就返回 `provider=amap`，并用 `useProxy` 标记是否配置了安全密钥（配了走同源代理 `app/api/map/[...proxy]` 由服务端注入 jscode，没配则前端直连高德）。

## 2026-10-01 · 投票功能立项（需求确认与方案定稿，未开工）

### 需求来源

过程中有**三次人工搬运**（候选 → 微信、投票 → 微信、结果 → 聊天记录），而且地址、人均、评分在搬运中全部丢失。

### 决策过程（用户逐条确认，勿再改）

第一轮（11:10）先出方案骨架与流程对比图，用户逐条拍板：

1. **单选**（一人一票）
2. 候选**只从已有地点库中挑**，不允许现场手输店名
3. 只做**手动结束**，不做定时截止
4. 结果**实时可见**
5. **任何人**可发起
6. 入口用**顶部第三个 tab**
7. **同时只允许一个进行中投票**，要新建必须先结束上一个
8. （追加需求）**投票历史要能查看**

第二轮（11:23）确认**结束权限同样对所有成员开放**，并要求把方案与需求落成文档、交 Codex 实现。

### 方案里几个必须记住的判断

- **结束权限必须比发起权限宽**：「同时只允许一个进行中」+「只有发起人能结束」会形成死锁——
  发起人不在场时所有人都发不了新投票。用二次确认 + 记录结束人 + 结果留在历史来兜住误操作。
- **「一人一票」是信任约束，不是防刷**：身份是浏览器本地令牌，清缓存或换设备即新成员。
  本期不做加固，靠公示投票人缓解。**这一点必须如实告知用户，不能给错误预期。**
- **候选不允许手输**：手输的店没有地址、坐标、封面、评分，点开是空卡片，等于又回到「把信息搬进群里」的老路。
  需要新候选就先添加地点（现有截图识别 + 自动定位已支持），再发起投票。
- **「实时可见」不是推送**：用「打开拉取 + 前台每 10 秒轮询」，不引入 websocket。
- **`poll_options.place_id` 不加外键**：加了会让现有「永久删除地点」被引用约束拒绝而失败——
  新功能弄坏老功能的典型场景。改为存 `place_name` 快照 + `LEFT JOIN places`，已登记为问题汇总 Q22。
- **单投票约束下沉到数据库**：用 SQLite 部分唯一索引 `ON polls(status) WHERE status='open'`，
  不能只靠前端隐藏按钮或接口「先查后写」（两人同时发起会双双成功）。

## 2026-10-08 · 修 `branchMatches` 分店判据（40 条美团实测暴露的定位瓶颈）

### 问题来源

40 条美团分享文案的只读实测里，「文案 → 结构化字段」零错误，但定位只有 **67.5%** 自动命中，**13/40（32.5%）落到「没找到这家分店」的候选待选**。人工复核发现其中约 11 条的首条候选其实就是目标店 —— 是 `lib/geo.ts` 的 `branchMatches()` 判不出来，不是数据缺失。

### 三处缺陷

1. **候选自带分店后缀时直接 `return`，不回退检查 pool**。实例：31 号「旺阁茶餐厅（笋岗店）」vs 候选「旺阁茶餐厅(宝岗路店)」，两侧地址**门牌同为「宝岗路100号」**，仍判 `false`。
2. **`coreName()` 删掉全部括号内容**。分店名恰恰常写在括号里，用它做分店比对等于把判据抹掉。叠加 `branchOf()` 只认**末尾**括号：「金泰食府(竹园店)地上停车场」这类括号后还有字的名字取不到分店名。
3. **判据方向单一**：只拿「文案的分店后缀」找候选，不拿「候选的分店后缀」比文案地址。实例：23 号美团写「翠竹店」、高德 POI 写「(圳通大厦店)」，而文案地址里就有「圳通大厦」——反向比对能命中。

另有一个认知修正：**高德 POI 名常常不带分店后缀，分店信息只在地址里**。如「威记肠粉王(木头龙店)」的地址是「翠竹街道华丽路**翠华花园**8栋1-3号」——高德拿片区名做了别名，真正的分店线索在地址字段。

### 改动（仅 `lib/geo.ts`）

`branchMatches(wanted, candidateName, candidateAddress, wantText)` 由「单向一条」改为**三条并列 + 一条兜底**：

1. `plainText(候选名 + 候选地址).includes(wantedKey)`
2. `wantSide.includes(candidateKey)` —— 反向比对
3. 两侧分店名相等 / 互相包含
4. `longestCommon(wantSide, plainText(候选地址)) >= 5` —— 门牌级证据兜底

新增 `plainText()`（去标点空白但**保留括号**）、`longestCommon()`（最长公共子串 DP）、常量 `ADDRESS_MATCH_MIN = 5`。`collectHits()` 增加第三参 `wantText`，`amapLocate` 两处调用均传 `` `${name}${address}` ``。

判据**只放宽、不收紧**：`branchKey` 为空（文案无分店信息）时仍按主体名算。门槛取 5 是拿实测校准的 ——「宝岗路100号」(7 字) 命中，「笋岗东路」(4 字) 不命中（33 号那家 VGM 广场店靠这条被正确挡住）。

识别名被品类污染成「小火雲椰子鸡火锅」→ 去重 7 字 {小,火,雲,椰,子,鸡,锅}；高德候选「润园四季椰子鸡火锅」含 5 个 → **5/7 = 0.714 ≥ 0.7 直接放行**；更接近的「四季椰林椰子鸡」只重合 3/7 反被挡掉。**品类词（椰子鸡火锅）在任何同品类店名里都会大面积重合**，把一个完全不同的品牌拉过门槛。且**地址证据全程没参与否决**。

**② 我把真值读错了一个字：不是「熵」是「煵」**

`IMG_3304` 的店名第 2 字，我原记为「熵」。两处独立证据推翻：
- **渲染比对**：把截图里的字与三种字体渲染的 `熵/煵/楠` 做归一化像素比对（先做紧边框归一，再算平均绝对差）。`煵` 0.2736/0.2910 压过 `熵` 0.2889/0.3086；`楠` 最差 0.3507。**对照组**（把「楼」放进候选 `楼/蘩/繁`）三个字体一致判成「楼」（0.2996/0.3072/0.3283 压过 繁 0.3724 起），证明方法本身能区分。
- **高德登记名**就是「小煵记·深圳本地菜(南新店)」@南新路南海台大厦 2068 号，与截图地址同栋。

所以真实链条是：截图「**煵**」（火+南）→ 模型输出「**楠**」（木+南）：右半边「南」认对了，**左偏旁「火」错成「木」**。

**为什么错**：送进模型前整屏 2796px 被等比压到长边 1600（`lib/image-compress.ts` 的 `preparePhoto`），店名行只剩约 **30px 高**；「火」（丷+人）与「木」（十+八）在这个尺寸下只差两三笔走向。叠加**模型的语言先验**——「楠」是常见字、「煵」是极生僻字，模型会往常见字上靠。同类错字（璽→雲、蘩→繁、嚎→豪）都符合「生僻字 + 小字号」这个形态。

**反例即证据**：这三个字**高德登记的就是正确写法**（「蘩楼(华强北总店)」@振华路 118 号、「Petit Oyster叫嚎(平安金融中心店)」@平安金融中心南塔 SL404、「小火璽」）—— 说明**用高德 POI 名回写展示名**这一招能直接修掉其中三个。
